1Identical field to the single-number screen, so the step up to Level 2 adds one control rather than replacing the screen.
2One thumb on a multiplier dial, not on the answer axis — it has no end stops in answer space, so it can neither clip a true value nor hint at its magnitude. The dial runs over uncertainty factors rather than over the answer axis, so unlike 4a it cannot leak the answer's order of magnitude at all.
3Continuous, not detented: the thumb rests at any factor and the live label reads it back. Coarse steps would quantise the very coverage the app measures, making the instrument partly responsible for the result — a user whose honest uncertainty is ×4 must not be forced to claim ×3 or ×10.
4Bounds are derived and shown live, so the user sees the actual claim being scored, in the same words the Feedback screen will use.
5Escape hatch to the two-field entry of 4b for asymmetric ranges. Same answer, recorded identically.
Trade-off. Sidesteps the log-scale problem: nothing is ever off-scale, the axis cannot leak an order of magnitude, and the dial's unit — "within a factor of N" — is the quantity the app is teaching. But it forces ranges symmetric in log space, which is wrong for bounded quantities (a percentage cannot exceed 100), and the bounds the user is judged on are one derivation away from what they typed.

Two other treatments of the range input, considered and not chosen. Kept for the record with their trade-offs as written.

1The instruction is restated every question; "90% sure" is the thing being trained, so it is never reduced to an icon.
2Axis is identical on every question, so its bounds carry no information about this answer. Decade labels tell the user what the slider covers without anchoring them.
3Fields and slider are two views of one value, bound both ways: dragging retypes the fields, typing moves the thumbs. Typing a value above 1B is allowed — the thumb parks at the end stop and the track shows a "»" overflow chevron.
Trade-off. One gesture sets both bounds and the whole scale is visible at once, so the user always knows what is on offer. But at 360 dp a decade is ~35 dp: a 3 dp slip changes the bound by ~20%, so precise ranges have to be finished in the fields — and the fixed end stops mean the axis can, in principle, clip an answer.

1Two fields, "At least" / "At most" rather than lower/upper. Focus is on the first; the second is a hint until typed. Same keyboard-first model as the single-number screen, so one habit covers both modes.
2Strip is a read-out only — it moves when the numbers change and cannot be dragged, which is why it can show the full 1 – 1B scale without inviting the user to fish for an answer on it.
3IME action moves to the second field, then to Submit, so the whole answer can be given without leaving the keyboard.
Trade-off. Exact at any magnitude, no gesture precision to learn, and it reuses the single-number screen's mechanics. But two numbers cost more taps than one drag, and because the strip is passive the width of a 90% range never becomes tangible — the user is less likely to feel that a range is too narrow, which is the habit the app is trying to break.
